## Problem Statement

Vibe-coders build personal-use apps with Claude in minutes, but face a deployment gap. The app works locally, then... nothing. It sits on localhost and dies. The existing options don't fit:

- **Vercel/Netlify** — designed for public-facing apps. Overkill for a personal expense tracker only you will ever use.
- **Manual VPS setup** — SSH, nginx, Docker, DNS, SSL. 1-4 hours even for experienced developers.
- **Lovable/Bolt/Replit** — build AND host on their cloud. You don't own the data. You pay per-app.

SelfStack's thesis: one command deploys your vibe-coded app to your own infrastructure, accessible from your phone via Tailscale. No public URLs, no domains, no auth to configure, no DevOps.

## Demand Evidence

- **Founder's own usage:** Runs vibe-costs (expense tracker) and a Monarch/NerdWallet clone on a Hetzner VPS via Docker + Tailscale. Uses them daily from his phone.
- **Economic argument:** 10 niche SaaS subscriptions at $10-30/mo = $100-300/mo. One Hetzner VPS = $5-20/mo. Claude builds the replacements for free.
- **Forum signals:** Deployment gap for vibe-coded apps is a recognized problem online. Multiple platforms (Hosting.com, VibeSDK, VibeForge) launched in 2026 specifically to solve it.
- **Gap in market:** Every competitor deploys to THEIR cloud. Nobody says "deploy to YOUR machine."
- **No external user validation yet.** This design is the validation step.

## Status Quo

When someone vibe-codes an app with Claude and wants to use it day-to-day:

1. **Most common:** App dies on localhost. Never used again.
2. **If motivated:** Deploy to Vercel (free tier). Works for static sites. Full-stack apps need environment variables, domain setup, billing. Wrong mental model for personal use.
3. **If technical:** SSH into a VPS, manually set up Docker, nginx, SSL. 1-4 hours per app. Doesn't scale to 10 apps.
4. **SelfStack today:** Founder runs `docker compose up` on his VPS, configures Tailscale Serve manually. Works but requires per-app DevOps knowledge.

## Target User & Narrowest Wedge

**Target user:** Technical-but-lazy developer. CAN SSH, CAN configure Docker, but doesn't want to waste time on DevOps for personal apps. Vibe-codes with Claude Code or Cursor. Has (or will get) a VPS. Wants the same "it just works" experience for hosting that Claude gives for building.

**Narrowest wedge:** A Claude Code slash command or MCP tool. You finish building an app, type `selfstack deploy`, and it's live on your Tailscale network in under 60 seconds. No configuration. No manifest file. No registry lookup. Just: detect what's in this directory, Dockerize it, deploy it, give me the URL.

## Constraints

- Must work with the existing SelfStack codebase (Go binary, Docker orchestration, port management, reverse proxy).
- Must integrate into the Claude Code workflow (moment of creation).
- Must not require the app developer to write a `selfstack.yml` manifest for the initial deploy — auto-detection or AI-generated manifest.
- Must work with Tailscale for private access (no public URLs required).
- Must support both local machine deployment and remote VPS deployment.
- Path to B (full personal PaaS with Cloud onboarding) must remain clear.

## Premises (revised after dual-model CEO review)

1. **Software is no longer a moat.** AI + open-source can clone any SaaS app. The remaining problem is hosting and lifecycle management.
2. **The value proposition is "replace your SaaS subscriptions," not "deploy your app."** Deploy is the mechanism; cost elimination is the pitch.
3. **VPS persistence is the key unlock.** Local deploy is a demo. The real product requires always-on infrastructure so apps survive laptop sleep, reboots, and network changes.
4. **Tailscale collapses networking for private access** — both personal (your devices) and enterprise (your team's Tailscale ACLs).
5. **The moat is lifecycle management, not deployment.** Dockerfile generation and stack detection will be commoditized. Backups, upgrades, secrets, health monitoring, auto-scaling recommendations across 10+ apps — that's the defensible product.
6. **Two-tier market:** Personal (replace 10 subscriptions with one VPS) and enterprise (replace $10/seat SaaS with one VPS for the whole team via Tailscale ACLs).
7. **The registry is not a follow-up — it's co-equal with deploy.** Open-source SaaS alternatives (crowdsourced, available on DockerHub) are how non-vibe-coders get value. Not everyone needs to build with Claude.
8. **Biggest risk is Claude itself.** Any AI can generate a deploy script. The defensible position is the runtime + registry, not the deploy command.

## Approaches Considered

### Approach A: "Deploy Command" — Validate with a Claude Code integration
Build a minimal `selfstack deploy` command that integrates into the Claude Code workflow. When you finish building an app, you say "deploy this to my SelfStack" and it SSHs to your VPS, Dockerizes, deploys, and returns a Tailscale URL. Leverages existing codebase for Docker orchestration and port management.

- **Effort:** S (human: ~1 week / CC: ~2 hours)
- **Risk:** Low
- **Pros:** Intercepts moment of creation, tests core hypothesis, leverages existing code
- **Cons:** Narrow distribution (Claude Code users only), no dashboard/store

### Approach B: "Personal PaaS" — Ship the existing CLI + Cloud onboarding
Polish the existing SelfStack CLI and build the SelfStack Cloud onboarding flow (provision a Hetzner VPS, install SelfStack + Tailscale automatically). User signs up, gets a VPS, and can deploy vibe-coded apps via CLI or dashboard. Full vision, minimum viable.

- **Effort:** L (human: ~2 months / CC: ~1 week)
- **Risk:** High — large investment before demand validated
- **Pros:** Full product vision, works for less technical users, dashboard stickiness

### Approach C: "Registry Flip" — Reposition as a vibe-app sharing platform
Build a registry where vibe-coders publish their AI-generated apps. Other users browse, discover, and deploy to their own SelfStack. Existing DockerHub and open-source apps serve as the initial catalog — no cold start needed.

- **Effort:** M (human: ~3 weeks / CC: ~3 days)
- **Risk:** Medium
- **Pros:** Network effects, solves discovery, differentiates from competitors
- **Cons:** Two-sided marketplace dynamics, quality control

## Recommended Approach

**Start with A, path to B.** The deploy command validates demand with the smallest investment. The existing codebase (Docker orchestration, port management, health checks, reverse proxy) provides the backend — the deploy command is a new entry point, not a rewrite.

### What "Deploy Command" looks like concretely

**Entry point:** `selfstack deploy` CLI command (also usable as a Claude Code slash command or MCP tool).

**Deploy flow (VPS-first, V1):**

V1 targets VPS deployment. Local deploy is supported but the VPS path is primary — persistence is the core value proposition. If the app dies when your laptop sleeps, you haven't solved the problem.

```
Developer finishes building an app with Claude
  -> "Deploy this to my SelfStack"
  -> selfstack deploy [--name app-name] [--env-file .env] [--remote user@host]

  1. Detect project type (Dockerfile? docker-compose.yml? package.json? go.mod?)
  2. If no Dockerfile: auto-generate one based on detected stack
  3. If no docker-compose.yml: auto-generate one
  4. Load .env file if present (or --env-file flag)
  5. If deploying to VPS (default): rsync project to VPS (excludes: node_modules, .git, __pycache__)
  6. Build Docker image on target (docker compose build)
  7. Allocate port (existing port manager)
  8. Start container with env vars injected (existing container manager)
  9. Configure reverse proxy route (existing proxy, exposed via single Tailscale Serve port)
  10. Health check (existing health checker)
  11. Return URL: https://<machine-name>.<tailnet>.ts.net (routed via proxy to app)

  Total time: <60 seconds for redeploys (warm cache).
  First deploy: 1-3 minutes depending on image pull/build time.
```

**Redeployment (app already running):**
```
selfstack deploy (same directory, app already exists)
  1. Detect that app-name is already deployed
  2. Rebuild image with latest code
  3. Stop old container (volumes preserved)
  4. Start new container with same volumes + updated image
  5. Health check
  6. Print "Updated <app-name>, accessible at <URL>"

  No blue-green in V1. Simple stop-then-start. Acceptable for personal apps
  where 5 seconds of downtime doesn't matter.
```

**Failure modes:**
- **Build fails (step 5):** Print Docker build error. No cleanup needed — nothing was started.
- **Container won't start (step 7):** Print container logs. Deallocate port. Clean up.
- **Health check fails (step 9):** Print health check error + container logs. Leave container running for debugging. User runs `selfstack logs <app>` to investigate.
- **Tailscale Serve fails (step 8):** Container is running but not accessible via Tailscale. Print error, tell user the local port they can access directly. Suggest checking `tailscale status`.
- **General principle:** No silent failures. Print what happened, print what to do next.

**Environment variables:**
- Auto-detects `.env` file in project root, injects as container env vars
- `--env-file path/to/.env` for explicit path
- `selfstack config <app> set KEY=val` for post-deploy config changes (existing config system)

**Auto-detection heuristics (V1 — simplest case per stack):**
- `docker-compose.yml` exists → use it directly
- `Dockerfile` exists → wrap in a compose file
- `package.json` exists → Node.js app, generate Dockerfile (node:22-slim, npm install, npm start)
- `go.mod` exists → Go app, generate Dockerfile (golang build + scratch)
- `requirements.txt` or `pyproject.toml` → Python app, generate Dockerfile (python:3.12-slim, pip install, python main.py)
- Fallback: error with "Can't auto-detect. Add a Dockerfile or docker-compose.yml."

**V1 non-goals for auto-detection:** No multi-stage builds, no native C dependencies (psycopg2, sharp), no monorepo support. If auto-detection produces a broken Dockerfile, the user (or Claude) edits it manually. The Dockerfile is generated into the project directory so it's always inspectable.

**First-time setup:**
```
selfstack init
  -> Verifies Docker is running locally
  -> Verifies Tailscale is running and authenticated
     (if not: "Run `tailscale up` to authenticate, then retry")
  -> Stores config in ~/.selfstack/config.yml
  -> One-time, <1 minute
```

**Tailscale integration details:**
- Requires `tailscaled` running and node authenticated (`tailscale status` returns OK)
- Uses `tailscale serve --bg <port>` to expose each app on the tailnet
- Apps accessible at `https://<machine-name>.<tailnet>.ts.net/<app-name>` (path-based routing)
- HTTPS certificates are automatic within the tailnet (Tailscale handles this)
- MagicDNS must be enabled in the Tailscale admin console (default for new tailnets)
- Cloudflare Tunnel remains available via `--tunnel cloudflare` flag for users who want public access. Not the default.

**What this reuses from existing codebase:**
- `internal/container/` — Docker SDK orchestration, port allocation
- `internal/proxy/` — reverse proxy routing (used for local access, Tailscale handles remote)
- Health check logic
- SQLite config store for tracking deployed apps

**What's new:**
- Project type auto-detection + Dockerfile/compose generation
- Tailscale Serve integration (default tunnel for personal use)
- `.env` file detection and injection
- Redeploy logic (stop old, start new, preserve volumes)
- `selfstack deploy` command in `cmd/`

**V1.1 (after validation): Enterprise tier**
- Multi-user access via Tailscale ACLs (team members access apps on the company VPS)
- Per-app access control (who can see which app)
- Usage monitoring and auto-scaling recommendations
- Managed backups and disaster recovery

### Path from A to B

Once the deploy command is validated:
1. **Add dashboard access** — `selfstack dashboard` opens the existing React UI showing all deployed apps, health status, logs
2. **Add the registry** — DockerHub + open-source apps are already available. The existing registry client just needs to point at a curated list of "SaaS replacements" (Linear alternatives, NerdWallet alternatives, etc.)

## Resolved Decisions

1. **Tailscale is the default.** Cloudflare Tunnel available via `--tunnel cloudflare` flag. Rationale: personal apps don't need public URLs, and Tailscale collapses the DNS/SSL/auth problem entirely.
2. **Auto-generated Dockerfiles target the simplest case per stack.** No native deps, no monorepos, no multi-stage builds in V1. If it breaks, the user (or Claude) edits the generated Dockerfile.
3. **VPS-first in V1.** Persistence is the core value prop. Local deploy is supported but secondary. SSH/rsync adds complexity but solves the actual problem (app stays alive 24/7).
4. **Route through existing reverse proxy, not path-based Tailscale Serve.** Most vibe-coded apps assume root "/". The existing reverse proxy handles per-app routing. Tailscale Serve exposes one port (the proxy). Each app gets its own subdomain via the proxy.
5. **Registry is co-equal with deploy in V1.** Curate 10-20 "SaaS replacements" as docker-compose templates. Not everyone needs to vibe-code their own — some users just want the open-source NerdWallet clone.

## Open Questions

1. **Claude Code integration mechanism:** Slash command, MCP tool, or just a CLI command that Claude can invoke via Bash? MCP is the cleanest integration but more work. V1 ships as CLI; MCP is on the path-to-B roadmap.
2. **App naming collisions:** What happens if the user deploys two different apps both called "app"? Auto-suffix with directory name? Error and require `--name`?

## Success Criteria

1. **Deploy works end-to-end:** `selfstack deploy` takes a vibe-coded app from current directory to running on Tailscale. Target: <60 seconds for redeploys (warm cache), <3 minutes for first deploy.
2. **Auto-detection works:** Successfully deploys Node.js, Python, and Go apps without manual Dockerfile creation.
3. **Someone else uses it:** At least one person besides the founder deploys an app using the command. This is the demand validation.
4. **Multi-app works:** 5+ apps running on one VPS, all accessible via Tailscale, no port conflicts, no resource issues.

## Architecture Decision: VPS Control Plane Model

**Decision (from autoplan eng review):** `selfstack serve` runs on the VPS as the control plane. `selfstack deploy` is a thin client that rsyncs files to the VPS then calls the VPS's REST API (`POST /api/apps/deploy`).

**Why this resolves the three eng review blockers:**
1. Remote execution: the API on the VPS handles all orchestration (same code path as local)
2. Routing: the proxy on the VPS handles routing (existing code works unchanged)
3. Single control plane: both local CLI commands and deploy use the same API

**Deploy flow (revised):**
```
Developer: selfstack deploy [--name app-name]
  1. Auto-detect project type, generate Dockerfile if needed
  2. rsync project files to VPS (~/.selfstack/apps/<app-name>/)
  3. POST /api/apps/deploy {name, env_vars} to VPS selfstack API
  4. VPS selfstack server: parse/generate manifest, build, allocate port, start, health check
  5. VPS selfstack server: register proxy route
  6. Return URL to user
```

**Init flow (revised for VPS-first):**
```
selfstack init
  -> Prompts for VPS SSH connection (user@host)
  -> Tests SSH connection
  -> Checks: Docker running? Tailscale authenticated? selfstack binary installed?
  -> If selfstack not installed on VPS: offer to install via SSH
  -> Starts `selfstack serve` on VPS (or verifies it's running as systemd service)
  -> Stores VPS config in ~/.selfstack/config.yml
```

**Manifest bridge:** Deploy generates a `selfstack.yml` on the VPS from auto-detected project info. This means existing commands (start, stop, logs, update) work on deployed apps without changes. The `apps` table gets a `source_type` column ('registry' vs 'deploy') and `repo_url` becomes nullable.

## Routing Decision

**Single model:** Tailscale Serve exposes one port (the SelfStack reverse proxy). The proxy routes by subdomain on the local network (`app-name.selfstack.local`). On Tailscale, apps are accessed via `https://<machine>.ts.net` with the proxy routing based on the `Host` header or a path prefix.

For V1: use port-based access as the simplest model. Each app gets its own Tailscale Serve entry: `tailscale serve --bg <port>` creates `https://<machine>.ts.net:<port>`. Simple, no routing conflicts, no DNS tricks. The proxy handles local subdomain routing.

For V1.1 (enterprise): evaluate Tailscale Funnel per-app or separate Tailscale nodes per app for ACL isolation.
